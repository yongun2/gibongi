# 04. 맵: 해시 테이블 내부와 함정

> 아직 설계 메모만 있는 섹션이다. 예제와 실습은 이 메모를 바탕으로 만든다.

> 선행 03 · 2.5h · 관련 변화: `clear`(1.21), `maps.Keys` 등 이터레이터(1.23), **Swiss table 구현(1.24)**

**핵심 질문**

1. Go 맵은 어떤 해시 테이블이고(1.24 Swiss table), 커질 때 무슨 일이 일어나나?
2. 왜 순회 순서가 매번 다르고, 왜 `m[k].f = v`는 컴파일되지 않나?
3. 맵을 함수에 넘기는 것은 슬라이스를 넘기는 것과 무엇이 다른가?
4. 원소를 다 지우면 메모리가 돌아오나? 동시에 쓰면 무슨 일이 생기나?

**README**

- ① 내부 동작
  - **맵 변수의 정체**
    - 맵 변수는 런타임 맵 구조를 가리키는 **포인터 하나(8B)**다. 그래서 함수에 넘기면 삽입·삭제가 모두 호출자에게 보인다(03의 슬라이스 헤더와 대조).
    - nil 맵: 읽기, `len`, `delete`, `range`는 되고 **쓰기만 panic**이다.
  - **Swiss table** **[RN 1.24, 블로그]**
    - 슬롯 8개가 한 그룹이고, 그룹마다 8바이트 제어 워드가 있다.
    - 해시 상위 57비트(H1)로 탐색을 시작할 그룹을 고른다. 하위 7비트(H2)는 제어 바이트에 저장해 두었다가 그룹 안 8슬롯을 한 번에 비교한다.
    - 테이블 하나는 최대 1024 엔트리다. 테이블이 여러 개면 디렉터리로 묶는다(extendible hashing).
    - 커질 때는 **테이블 하나만 분할**한다. 그래서 한 번의 삽입이 복사하는 양은 1024개 이하다.
    - 마이크로벤치 최대 60%, 실제 앱 기하평균 약 1.5% CPU 개선 **[블로그]**.
  - **무작위 순회**: 맵마다 해시 시드가 다르고 순회 시작 위치도 무작위다. 순서에 의존하는 코드를 일부러 깨뜨리려는 설계다.
  - **원소에 주소가 없다**: 성장 중에 원소가 옮겨질 수 있어 원소의 주소를 줄 수 없다. 그래서 `m[k].f = v`가 불가하다.
  - **순회 중 수정**: 삭제는 안전하다. 삽입한 원소는 보일 수도 있고 안 보일 수도 있다(스펙).
  - **줄어들지 않는다** **[로컬]**: `map[int][128]byte`에 100만 개를 넣으면 288MiB다. 전부 `delete`해도, `clear`해도 288MiB 그대로이고, `m = nil`로 맵을 버려야 0이 된다.
  - **동시 쓰기**: 런타임이 쓰기 플래그로 감지해 `fatal error: concurrent map writes`를 낸다. recover로 잡을 수 없고 프로세스가 끝난다.
  - **키 규칙**
    - 키는 comparable이어야 한다.
    - 인터페이스 키에 비교 불가 동적 타입이 들어가면 런타임 panic이다.
    - NaN 키는 넣을 때마다 새 엔트리가 된다.
    - 복합 키에는 구조체 키를 쓰는 것이 관용이다.
  - **표준 패키지**: `maps.Keys/Values/All`은 이터레이터를 돌려준다 → `slices.Sorted(maps.Keys(m))`. `maps.Clone`은 **얕은 복사**다.
- ② 차이

  | Java | Go |
  |---|---|
  | HashMap: 체이닝(버킷에 8개 넘으면 트리), 로드팩터 0.75에서 2배 rehash를 한 번에 | 그룹 단위 오픈 어드레싱, 테이블 하나씩 분할 |
  | 순회 순서가 해시 순으로 결정적 → 테스트가 우연히 순서에 의존 | 순회 순서 무작위 |
  | LinkedHashMap(삽입 순서 유지) | 없음 → 키 슬라이스를 따로 유지 |
  | fail-fast 이터레이터(`ConcurrentModificationException`) | 순회 중 수정 허용, 동시 쓰기는 fatal |
  | `equals/hashCode` 직접 구현 | comparable 구조체 키는 자동 |
  | Set | `map[K]struct{}`(값 0바이트) |

- ③ 판단 기준
  - 크기를 예상할 수 있으면 `make(map[K]V, n)`(벤치로 할당 차이 확인).
  - 출력이나 테스트에 순서가 필요하면 키를 정렬한다.
  - 키가 0..N으로 촘촘하면 맵 대신 슬라이스를 쓴다(벤치: 페이지 번호 → 프레임).
  - 크게 키웠다가 줄어든 맵을 오래 유지해야 하면 새 맵으로 옮겨 담는다.
  - 동시 접근이 필요하면 13장의 `Mutex+map`이 기본이다.
  - 키를 `fmt.Sprintf("%d-%d")`로 만들지 말고 구조체 키를 쓴다.
- 함정
  - 구조체 필드 맵의 초기화를 빠뜨려 nil 맵에 쓴다.
  - 테스트가 순서에 의존한다.
  - `maps.Clone` 뒤 값 슬라이스가 공유된다.
  - 동시 쓰기로 fatal error가 난다.
  - range의 `v`도 복사본이다.

**예제**

| 예제 | 보여 주는 것 | 관찰 |
|---|---|---|
| `iterationOrder` | 같은 맵 100회 순회 중 첫 키가 달랐던 적 있음 → `true`. 정렬 후 출력은 결정적 | 출력 |
| `nilMap` | 읽기 0, 쓰기 panic `assignment to entry in nil map` | recover 메시지 |

| `notAddressable` | `m[k].f = v` 컴파일 에러 | `observe.CompileErrors` |
| `noShrink` | 채움 > 200MiB, 전부 delete/clear 후에도 > 200MiB, `m=nil` 후 < 10MiB | `runtime.ReadMemStats` |
| `concurrentWritesFatal` | 서브프로세스 출력에 `fatal error: concurrent map writes`, 종료 코드 2 | `observe.Run` |
| `structKey` | `(pid, vpn)` 구조체 키 | 출력 |
| `Benchmark*` | 크기 힌트 유무, 구조체 키 vs `Sprintf` 키, 촘촘한 키에서 `map[int]int` vs `[]int` | `--bench` |
